# Sign-in links and HintWise email

The pure logic of three Supabase Edge Functions (design: `docs/platform.md`,
"Sign-in links and abuse limits" and "Email footer, logo and opt-out"):

- `sign-in-link` (`platform/supabase/functions/sign-in-link/index.ts`): apps
  call it instead of `supabase.auth.signInWithOtp`. It spaces out links,
  asks for a Cloudflare Turnstile check when one address, browser or network
  asks too often, creates the link with Auth's admin API and emails it
  through Resend.
- `auth-email-hook` (`platform/supabase/functions/auth-email-hook/index.ts`):
  Supabase Auth's Send Email hook. Once it is switched on, Auth hands it
  every auth email. It refuses the sign-in emails (magic link, sign-up,
  code, recovery) unless they are for an app outside HintWise that shares
  the project. It sends the account emails (invite, email change,
  reauthentication, notices) for every app. All of it goes through the same
  per-address ladder.
- `email-optout` (`platform/supabase/functions/email-optout/index.ts`): the
  page behind every email's "Stop all email from HintWise" link, and the
  support commands of `supabase-admin.mjs email-optout`.

The Deno entries only pass `Deno.env`, `fetch` and `EdgeRuntime.waitUntil`
to the handlers here. Tests: `platform/test/signin-*.test.ts`.

## Request and answers

`POST <SUPABASE_URL>/functions/v1/sign-in-link` from a page of a deployed
app. The template sends the anon key as `apikey`, but the function needs no
JWT (`verify_jwt = false`). JSON body:

```json
{ "email": "ann@example.com", "redirectTo": "https://pluck-lab.hintwise.org/app",
  "app": "pluck-lab", "browserId": "<localStorage hintwise.browserId>", "turnstileToken": "<optional>" }
```

| HTTP | Body | When |
|---|---|---|
| 200 | `{ status: 'sent' }` | the email went out |
| 200 | `{ status: 'suppressed', message }` | the address turned HintWise email off; nothing was sent. `message`: "This address asked HintWise not to send it email. Sign in with Google instead, or write to support@hintwise.org from this address to turn email back on." Checked after the ladder and the challenge, just before the link would be made; logged `refused` |
| 429 | `{ status: 'wait', retryAt }` | too early for this address or browser, or the IP network is over 100 requests an hour; `retryAt` is an ISO time |
| 403 | `{ status: 'challenge', siteKey, failed? }` | a Turnstile check is needed; `failed: true` when the token did not pass |
| 503 | `{ status: 'error', message: 'Email sign-in is paused; try Google' }` | a check is due but `TURNSTILE_SECRET` is unset |
| 400 / 413 | `{ status: 'error', message }` | bad body |
| 403 | `{ status: 'error', message }` | the Origin is not a page of an allowed app |
| 500 / 502 / 503 | `{ status: 'error', message }` | database, Auth or Resend trouble, or the function is not configured |

**Allowed apps.** A link only returns to `https://<label>.hintwise.org/<path>`
when `<label>` is:
- a deployed app (`app-hosts.ts`, generated from each `target.yml`'s
  `netlify.customDomain`, mapped by `scripts/domains.mjs`, or its `siteName`);
- or one of `EXTERNAL_APP_LABELS` (`stepwise`, and from 12 Nov `photo2pgn`, deployed from its own repository pisan-labs/photo2png, to be renamed photo2pgn before its first deploy).

`auth`, `www` and the other `NON_APP_LABELS` are never allowed. The Origin
and CORS follow the same list.

After adding an app: run `npm run app-hosts` in `platform/`, commit, and
redeploy sign-in-link. `test/signin-app-hosts.test.ts` fails in CI while the
file is stale.

**The link.** It is the page's origin and path, with
`token_hash=<hashed_token>&type=email&email_hint=<a***@example.com>`. The
query and fragment of `redirectTo` are dropped. The app calls
`supabase.auth.verifyOtp({ token_hash, type: 'email' })`, which works in any
browser.

Before verifying, the template checks the `email_hint`. It accepts only
`/^[^@\s]\*{3}@[a-z0-9.-]{1,253}$/i`, at most 260 characters, and ignores
anything else. Then:
- another account signed in: it asks first, "Switch to a***@example.com?";
- an account with the same masked address signed in: it says "Already
  signed in as a***@example.com" and offers "Use the link instead". Masks
  collide, so the link is never dropped silently.

The link expires when
Auth's `mailer_otp_exp` says (about an hour). The email goes to the address
as typed; Auth gets it lower-cased.

## Limits

- **Keys.**
  - The address counts as its canonical mailbox: lower-cased, any `+tag`
    dropped, and for `gmail.com` and `googlemail.com` the dots dropped and
    the domain `gmail.com`.
  - The IP counts by network: an IPv4 address as it is, an IPv6 address by
    its /64, and an IPv4-mapped address as its IPv4 address.
  - The IP is read from `cf-connecting-ip` when that header is there,
    otherwise from the **right-most** `x-forwarded-for` entry (the one the
    last proxy added; the left-most is what the client sent).
  - The value counts as `unknown` when either:
    - it does not parse as an IPv4 address (four decimal octets, no leading
      zeros) or an IPv6 address;
    - it is not a visitor's own address: private (10/8, 172.16/12,
      192.168/16, fc00::/7), loopback, link-local, CGNAT 100.64/10, "this
      network", multicast and reserved, or one of Cloudflare's published
      proxy ranges.

    The list is hard-coded in `keys.ts` with its date (10 Nov 2026).
  - An unknown IP gets no hard per-IP limit (`p_ip_limit` null), because
    every such request shares one key and one busy network would throttle
    everyone. It makes the challenge due instead.
  - **To check live after the deploy (the parent session):** which header
    Supabase's edge passes. Send one request with a made-up
    `X-Forwarded-For` and check its `ip_hash` matches an ordinary request
    from the same machine.
- **Hard per-IP limit.** It applies to known IPs only and is checked first,
  in `sign_in_begin` and in `sign_in_log`. With 100 requests of any outcome
  from the IP network in the last hour, the answer is a wait until the
  oldest of them leaves the hour, and no row is written. A flood from one
  network cannot fill the table: 100 rows an hour at most.
- **Ladder per address and per browser.**
  - Between links the wait is 1, 3, 5, 8, 13 and 21 minutes, then the sum of
    the previous two (34, 55, 89, ...), capped at 24 hours.
  - Only links sent since the key's last quiet day count: 24 hours with no
    counted request for the key resets it. Invalid and refused rows are not
    counted.
  - A request still being decided (`pending`, for at most 5 minutes) counts
    as a link being sent, and `sign_in_begin` locks the address and the
    browser first, so parallel requests cannot send several links at once.
  - The later of the two waits wins. A wait is answered before any
    challenge.
- **Challenge.** It is due when any of these holds:
  - this request is the 10th or later in 24 hours for the address, or for
    the browser (invalid and refused rows not counted);
  - it is the 21st or later in an hour from the IP network;
  - the IP is unknown;
  - more than 100 links went out project-wide in the last hour (the brake).
- **The check.**
  - A form POST to Cloudflare's siteverify with `secret`, `response` and
    `remoteip`, with a 10-second timeout.
  - A token passes only when `success` is true, `action` is `sign-in` and
    `hostname` is `hintwise.org` or ends in `.hintwise.org`.
  - A token over 2048 characters is refused without a call. Tokens are
    single-use and never checked twice.
  - Any failure is `challenge_failed`, HTTP 403.
  - While `TURNSTILE_SECRET` is unset, a due challenge pauses email sign-in
    (503, outcome `error`) instead of sending.
  - The site key is public: `TURNSTILE_SITE_KEY` in `turnstile.ts`, the same
    as `platform/supabase.json` `turnstileSiteKey`; the env may override it.

## Log and alerts

Every request is one row in `platform.sign_in_requests`, written through RPCs
(`platform/supabase/shared/0002_sign_in.sql`). The only exception is a
request over the hard per-IP limit, which writes no row.

A row holds `created_at`, `app`, `outcome` (`sent`, `wait`, `challenge`,
`challenge_failed`, `refused`, `error`, `invalid`), `detail`, and the
HMAC-SHA256 hashes of the canonical mailbox, the IP network and the browser
id. No address, IP or browser id is stored.

Rows older than 30 days are deleted, up to 200 per logged request, with
`for update skip locked`, so parallel prunes do not wait on each other. The
owner finds an address's rows by hashing `email:<canonical mailbox>` with
`SIGN_IN_HASH_KEY`.

RPCs and not table writes: each step is one round trip and one transaction,
which the per-address lock needs. The functions are security invoker with
`search_path = ''`, executable only by `service_role`. Anon and authenticated
have no access to the tables or the functions.

Alerts go to `ADMIN_EMAIL` from `builder@hintwise.org`, at most one per kind
an hour (`platform.sign_in_alerts`):

| Kind | Rule |
|---|---|
| `many-addresses` | one IP or one browser asked for links to 5 or more different addresses in an hour |
| `address-repeated` | one address was asked for 5 or more times in an hour |
| `challenge-failures` | 3 or more failed checks from one IP in an hour |
| `volume` | more than 100 links sent across all apps in an hour |
| `bypass` | `auth-email-hook` refused an email |

The emails show counts, the first 16 characters of the hashes, and a query
for the rows. Only `address-repeated` names the address, so the owner can
tell a visitor who cannot find the email from someone filling a stranger's
inbox.

## Send Email hook

Auth signs each call with Standard Webhooks (`webhook-id`,
`webhook-timestamp`, `webhook-signature`). The secret, `SEND_EMAIL_HOOK_SECRET`,
is in the `v1,whsec_<base64>` form, and a timestamp more than five minutes
off is refused.

The hook answers HTTP 200 with `{ error: { http_code, message } }` when Auth
should fail the app's request with that status and message, and `{}` when
the email went out. Any other status reaches the app only as a bare 500.

The host is the payload's `redirect_to` host, else its `site_url` host.
`HOOK_EXTERNAL_HOSTS` holds the hosts of the apps outside HintWise on this
project: a comma list, `*.` for a wildcard, never a hintwise.org name.

| `email_action_type` | What the hook does |
|---|---|
| `magiclink`, `signup`, `email`, `recovery` for a host in `HOOK_EXTERNAL_HOSTS` | sent through the ladder: a link to `<SUPABASE_URL>/auth/v1/verify?token=<token_hash>&type=<type>&redirect_to=<redirect_to>`, or the code for `email` |
| the same four for a hintwise.org page or an unknown host | refused with 403 "Use the HintWise sign-in-link service", logged `refused`, raises `bypass` (HintWise apps send these through sign-in-link) |
| `invite`, `email_change`, `reauthentication` and every `*_notification`, for every host | sent through the ladder |
| any other type | refused the same way |
| `magiclink`, `signup`, `email`, `recovery` and every `*_notification` the plan sends, for an address on the opt-out list | answered as sent (`{}`) with nothing sent, before the ladder; logged `refused`, detail `suppressed, answered as sent`; no bypass alert. A refusal would tell anyone asking Auth for a recovery that the account exists and opted out (Auth answers an unknown address's recovery with 200 and sends nothing), and Auth only logs a failed notice |
| `invite`, `email_change`, `reauthentication` for an address on the opt-out list | refused with 403 "This address asked HintWise not to send it email. Write to support@hintwise.org from this address to turn email back on.", before the ladder; logged `refused`, detail `suppressed`; no bypass alert. An email change sends neither message when either address is on the list |

How Auth reads those answers (checked 11 Nov 2026):

- Supabase's Send Email hook page
  (https://supabase.com/docs/guides/auth/auth-hooks/send-email-hook):
  "An empty response with a status code of 200 is taken as a successful
  response."
- Supabase Auth's source (`supabase/auth`, `internal/api`): `recover.go`
  answers an unknown address with 200 and `{}` and sends nothing, and fails
  a known address's request with the hook's error (`sendPasswordRecovery`
  in `mail.go` returns it); `magic_link.go` does the same for magic links.
  Every notice is sent after the change and a failure is only logged:
  `user.go` "we don't want to fail the whole request if the email can't be
  sent" (password changed), and the same in `verify.go` (email changed),
  `identity.go` (identity linked, unlinked) and `mfa.go` (factor enrolled,
  unenrolled).

Every email the hook sends goes through `sign_in_begin`, keyed by the
recipient's canonical mailbox, with the fixed `hook` IP key, no browser and
no per-IP limit. A due wait refuses it (429).

An email change sends one message to each address (`token_hash_new` to the
current address and `token_hash` to the new one, since Supabase's names are
reversed), each through its own ladder. When one address must wait, neither
message goes. A change between two `+tags` of one mailbox is one ladder
step. `email-hook check` prints which types are refused or sent for which
hosts.

`email-hook check` and `email-hook on` refuse while an app in this repo
still calls `signInWithOtp`, `signUp` or `resend` (`--allow-otp-apps`
overrides). `on` also refuses with an empty `HOOK_EXTERNAL_HOSTS`, because
every external app would lose its email (`--accept-external-breakage`
overrides).

## Email footer, logo and opt-out

Every email the functions send (`email.ts renderEmail`) has:

- **Header.** The logo, `<img>` of `hintwise-wordmark-email@2x.png` at
  `width="100" height="28" alt="HintWise"`, on a small white panel, when
  `EMAIL_LOGO_URL` is an https URL on hintwise.org (`emailLogoUrl`, the one
  place the setting is read); else the text wordmark "HintWise" in deep
  indigo `#312E81`, bold, 18px.
- **Colours.** Body text has no colour of its own. The Sign in button is
  white on deep indigo; links are deep indigo and underlined; a
  `prefers-color-scheme: dark` rule lightens links (`#A5B4FC`) and the text
  wordmark (`#E0E7FF`) in clients that read it. Coral is only in the logo.
- **Reply-To** `support@hintwise.org` (Resend `reply_to`), alerts included.
- **Footer** (visitor emails, not the owner's alerts), text and HTML, in
  this order: why this address got it (one line per type, `WHY` in
  `email.ts`); "Questions or trouble signing in? support@hintwise.org (or
  just reply)."; "HintWise builds tools for small businesses, startups and
  educators. More apps: studio.hintwise.org"; "Stop all email from
  HintWise" (the recipient's opt-out link) "(sign-in links too)". Without
  `EMAIL_OPTOUT_SECRET` the last line names support instead.

**The tokens.** Both are HMAC-SHA256 under `EMAIL_OPTOUT_SECRET`,
base64url, checked with WebCrypto verify (constant time), canonical
spelling only, over a text that names their purpose:

| Token | Where | Signed text | Does |
|---|---|---|---|
| stop, `v1.<mailbox hash>.<sig>` | the footer link `https://auth.hintwise.org/functions/v1/email-optout?t=<token>`, the same in every email to the address | `hintwise-email-optout:stop:v1:all:<hash>` | stops email only; never expires |
| undo, `u1.<mailbox hash>.<expiry>.<sig>` | only in the "Done" page's Undo form (a POST body, never a URL) | `hintwise-email-optout:undo:u1:all:<hash>:<expiry>` | turns email back on only, until `<expiry>` (Unix seconds), one hour after the stop |

So anyone who sees one email can stop that address's email (as with any
unsubscribe link), but nobody can turn it back on with that link. The
owner of the address can press Undo for an hour; after that, only support
turns email back on. The mailbox hash is the sign-in log's key, HMAC-SHA256
of `email:<canonical mailbox>` under `SIGN_IN_HASH_KEY`, so the URL has no
address and a `+tag` or Gmail dot variant is the same address.

**The page** (`email-optout`, `verify_jwt = false`). It is served on the
custom domain because Supabase rewrites a GET's `text/html` to `text/plain`
on `*.supabase.co`.

| Request | Answer |
|---|---|
| `GET ?t=<stop token>` (or HEAD) | 200, "Stop all email from HintWise to this address?" (sign-in links included; Google sign-in still works) with a form that POSTs `t` and `action=stop`. Reads and changes nothing. A bad token (or an undo token): 400 "This link does not work" |
| `POST t=<stop token>&action=stop` (form) | `email_optout_set`, idempotent; 200 "Done" with an Undo button carrying a fresh undo token, and "write to support@hintwise.org from this address" for later |
| `POST t=<undo token>&action=undo` (form) | while the undo token is valid: `email_optout_clear`, idempotent; 200 "Email from HintWise is on again" with a Stop button (the stop token). Expired: 400 "This Undo button has expired", nothing changed |
| a stop token with `action=undo`, an undo token with `action=stop` | 400 "This link does not work", nothing changed |
| `POST application/json` `{ action: 'status' \| 'add' \| 'remove', email }` with the service-role key (`Authorization: Bearer`, or `apikey` for a `sb_secret_` key) | support: the function hashes the address and runs the RPC with the caller's key, so Postgres grants decide; answers with the 16-character hash prefix, never the address. `remove` clears every scope |
| without `EMAIL_OPTOUT_SECRET` | 503 "This page is not ready yet" |

Every page: no script, works without JavaScript, CSP `default-src 'none'`
(plus `img-src` for the logo's origin), `form-action 'self'`, no framing,
`no-referrer`, `no-store`, `noindex`. Only a token that verified (or one
made by the function) is echoed into the page, escaped; the page never
knows the address.

**Support** (`supabase-admin.mjs email-optout`, address in the workflow's
masked `email` input; the log shows only the action, the time and the hash
prefix):

- `add` stops all email for the address. Run it on any request: it can
  only stop email.
- `remove` turns all of it back on. Run it **only** on a request sent from
  that address that passes DMARC (check the `Authentication-Results`
  header), or after a confirming reply from it. Anyone can claim to own an
  address; only its mailbox can confirm it.
- `status` shows whether the address is on the list.
- On the first live run, check that the functions gateway passes a
  `sb_secret_` service key through to the function in `Authorization:
  Bearer` (or `apikey`) with `verify_jwt = false`: the code accepts both,
  but this has not been seen live (the repo secret may be a legacy JWT,
  which is known to work).

**The list** is `platform.email_optouts` (`0003_email_optout.sql`): one row
per mailbox hash and scope (`all` now; `app:<slug>` reserved for per-app
opt-outs with the app-notify sender, which `email_optout_check(hash,
scopes)` already takes), with `via` (`link` or `support`) and `created_at`.
RLS on, no policies, service role only, RPCs `email_optout_check`,
`email_optout_set`, `email_optout_clear`, `email_optout_status`.

**Failures send nothing.** When `email_optout_check` fails (or 0003 is not
applied yet), sign-in-link answers 500 and the hook refuses. So the
migration goes before the deploys, and `deploy-function` refuses to deploy
sign-in-link or auth-email-hook until `optout-ready` sees
`email_optout_check` answer.

**What an opted-out address cannot do.**

- Get a sign-in link from sign-in-link: it answers `suppressed` (Google
  sign-in still works).
- Get any Auth email through the hook. Sign-in emails and notices are
  answered as sent and dropped; invite, reauthentication and email change
  are refused (403). So an opted-out user cannot change their account's
  email address (in either direction: from or to an opted-out address)
  until they turn email back on through support.

**Where the opt-out does not hold (fail open).**

- `email-hook off`: Auth then sends its own emails directly, without the
  hook, so it ignores the opt-out list (sign-in-link still checks it).
- Rotating `SIGN_IN_HASH_KEY` or `EMAIL_OPTOUT_SECRET`: the list is keyed by
  the hash, so a new hash key silently drops every opt-out (and every
  sign-in ladder), and a new opt-out secret breaks every stop link already
  sent. Never rotate either without migrating the table (re-hashing needs
  the addresses, which are not stored, so in practice: never).

**Canonical mailbox: known gaps.** The canonicalisation drops `+tags`
everywhere and Gmail's dots, nothing else. Other aliases of one mailbox
count as different addresses, for the ladder and for the opt-out:

- Yahoo's `-` disposable addresses (`name-keyword@yahoo.com`);
- Fastmail's subdomain addressing (`anything@name.fastmail.com`);
- iCloud's aliases and Hide My Email addresses (`@icloud.com`, `@me.com`,
  `@mac.com`, `@privaterelay.appleid.com`);
- any domain's own aliases and catch-alls.

Opting out one of them leaves the others getting email; each has its own
footer link.

## Function secrets

`SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` come with every function. The
"Supabase admin" workflow's `set-sign-in-secrets` sets the rest, through a
private env file (umask 077, removed on exit), never as command-line
arguments:

- `RESEND_API` and `ADMIN_EMAIL`, from the repo secrets of the same names.
- `TURNSTILE_SECRET`, from the repo secret `TURNSTILE_SECRET` (or `TURNSTILE_SECRET_KEY`). The step
  exits 1 without it.
- `TURNSTILE_SITE_KEY`, from the repo variable or secret of that name, else
  the committed public key.
- `HOOK_EXTERNAL_HOSTS`, from the auth config: the `external-hosts` command
  takes the redirect allow-list and the site URL hosts, minus hintwise.org
  and names without a dot. The host names are printed, since they are not
  secret. Rerun the step after changing the allow-list.
- `SIGN_IN_HASH_KEY`, `SEND_EMAIL_HOOK_SECRET` and `EMAIL_OPTOUT_SECRET`,
  generated once (64 hex characters for the opt-out secret) and never
  rotated by the step.
- `EMAIL_LOGO_URL`, from the repo variable of that name, else the brand
  bucket's `hintwise-wordmark-email@2x.png` on the custom domain, and only
  once that URL answers `image/png` (run `brand-upload` first). Unset, the
  emails and the opt-out page show the text wordmark.

`email-hook on` replaces `SEND_EMAIL_HOOK_SECRET` with a fresh value that it
also gives to Auth.
